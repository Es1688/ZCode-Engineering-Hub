# ADR-0002: Принудительное исполнение Level 0 через hooks

- **Статус:** предложено (вступает в силу после вашего решения; режим `enforce` включается отдельно, по критериям ниже)
- **Дата:** 2026-10-01
- **Затрагивает:** Level 0 (`~/.zcode`), `it/zcode/hooks/guard/`, §6 техпроекта
- **Связано:** ADR-0001, ZCODE-HUB-DESIGN §6 (режимы × Level A–D), Фаза III

## Контекст

Правила Level 0 (git-гейты, опасные операции, секреты, эталонные данные) исполняются «по доброй воле» модели: она читает `AGENTS.md` и соблюдает его. В истории 42% сессий шли в `yolo`, где ZCode подтверждений не запрашивает вовсе. Формальной преграды между ошибкой модели и `git push` или `rm -rf` нет.

Эксперимент 01.10.2026 на вашей сборке ZCode (probe-hook, события из `~/.zcode/hooks/probe/`) дал факты:

| # | Факт | Источник |
|---|---|---|
| 1 | `PreToolUse` срабатывает в `build`, `edit`, `yolo` для `Bash`, `Write`, `Read` и мета-инструментов (`ExitPlanMode`); hook получает полную команду / путь | events.jsonl |
| 2 | `deny` из hook **действует в `yolo`**: `Bash` и `Write` с маркером остановлены, файлы не созданы, `echo` без маркера прошёл | guard.jsonl, ответ агента, проверка диска |
| 3 | Модель получает текст причины отказа дословно и обходной путь не искала | ответ агента |
| 4 | Поле `mode` ненадёжно: `SessionStart` показывает режим прошлой сессии, в сессии с `plan` события несут `build`/`edit` | events.jsonl |
| 5 | `riskLevel` грубый: у любого `Bash` он `high/system` (даже `echo`), `Write` — `medium/workspace`, `Read` — `low/none` | events.jsonl |
| 6 | `PermissionRequest` приходит только в `build` (на `Write`, `ExitPlanMode`); в `edit` и `yolo` ZCode сам ничего не спрашивает | events.jsonl |

Не проверено: решение `ask`; `deny` в `build`, `edit`, `plan`; вызовы субагентов; поведение ZCode при падении hook.

Проверка 09.10.2026 (workflow-проба субагентов, прогон dwfrun-64bad652): вызовы субагентов workflow проходят через `PreToolUse` — 5 проб из 5 зафиксированы в `guard.jsonl` с ожидаемыми правилами (Bash: G-READ-SECRET, G-PUSH, G-PIPE-TO-SHELL; Write и Bash: G-WRITE-OUTSIDE), решения `ask`×4 / `deny`×1, `effective=allow` в shadow; sid субагентов атрибутируются отдельно от родительской сессии (`ctor_1_1`, `ctor_2_1`), параллельная работа субагентов ошибок hook не дала. Не проверялись: блокировка в `enforce`, субагенты инструмента `Agent` (вне workflow).

## Решение

1. **Слой принуждения** — один hook `PreToolUse` (`guard.py`), общий для всех режимов. Решения принимаются по инструменту, команде и пути, **не по полю `mode`** (факт 4) и не по `riskLevel` (факт 5).
2. **Правила** сопоставлены Level 0; каждое имеет ID, Level и действие по умолчанию:

| ID | Level | Действие | Что ловит |
|---|---|---|---|
| G-PUSH | C | ask | `git push` |
| G-MERGE-MAIN | C | ask | `git merge` на main/master, `gh pr merge` |
| G-RELEASE | C | ask | `gh release`, `npm/cargo/poetry publish`, `twine upload`, `docker push` |
| G-PUSH-FORCE | D | deny | force/delete/mirror push |
| G-GIT-DESTRUCTIVE | D | ask | `reset --hard`, `clean -f`, `branch -D`, `stash drop/clear`, `filter-branch` |
| G-ADD-SECRET | D | deny | `git add` файла секретов (по факту наличия в рабочем дереве, с учётом `.gitignore`) |
| G-RM-CRITICAL | D | deny | `rm -r` корня, `~`, корня проекта, его предков, `.git`, `~/.ssh`, `~/.zcode` |
| G-RM-RECURSIVE | B | ask | прочий `rm -r`, `find -delete` (вне `/tmp`) |
| G-WRITE-PROTECTED | D | deny | запись в `~/.ssh`, `~/.zcode/hooks`, `~/.zcode/cli`, `~/PROJECTS`, системные каталоги |
| G-WRITE-ZCODE | D | ask | прочие записи в `~/.zcode` |
| G-WRITE-REFDATA | D | deny | запись в `DATASTOR`, `REPORTS`, `legacy` внутри workspace (список настраиваемый) |
| G-WRITE-OUTSIDE | B | ask | запись вне workspace и вне `/tmp` |
| G-READ-SSH | D | deny | чтение приватных ключей `~/.ssh` |
| G-READ-SECRET | B | ask | чтение `.env*`, `*.key`, `*.pem`, `~/.zcode` (кроме `.md`) |
| G-PIPE-TO-SHELL | D | deny | `curl \| sh`, `base64 -d \| sh`, `bash -c "$(curl …)"` |
| G-SUDO | D | ask | `sudo`, `doas` |
| G-SQL-DESTRUCTIVE | D | ask | `DROP`, `TRUNCATE TABLE` |
| G-SYSTEM | D | deny | `mkfs`, `shutdown`, запись в блочные устройства |

   Level A (чтение, обычные записи в workspace) не блокируется.
3. **Фазирование.** Режимы `off` / `shadow` / `enforce` в `guard.json`. Старт: **shadow**: hook решает и пишет `would`-решение, но ничего не блокирует.
   **Критерии перехода в `enforce`:** (а) не менее 7 дней и 5 рабочих сессий минимум в двух проектах; (б) отчёт `guard.py --report` просмотрен целиком, по каждому правилу ложные срабатывания либо исправлены, либо приняты осознанно; (в) нет записей с `error`, `ms` в разумных пределах (сейчас единицы миллисекунд); (г) пройден тест `ask` (см. п. 5).
4. **Отказ без обхода.** Текст отказа сообщает правило, Level и просит модель не искать обходной путь, а обратиться к вам.
5. **`ask` против `deny`.** Для Level B/C предпочтительно «спросить у пользователя». Поддержка `ask` проверяется тестом C (probe). Пока не подтверждена, флаг `ask_supported=false` и `ask` исполняется как `deny` (`ask_fallback`).
6. **Level C: явное разрешение.** Пользователь вручную создаёт файл `~/.zcode/hooks/guard/allow-level-c`; на `allow_once_ttl_min` (10 мин) правила Level C (G-PUSH, G-MERGE-MAIN, G-RELEASE) снимаются. Level D токеном не снимается. Модель не может создать токен: запись в `~/.zcode/hooks` под G-WRITE-PROTECTED.
7. **Отказоустойчивость: fail-open + мониторинг.** Любая внутренняя ошибка пропускает вызов и пишется в лог (иначе баг hook парализует работу). Компенсация: `guard.py --doctor` (проверяет регистрацию, `hooks.enabled`, ошибки ZCode `config.file.invalid` / `hook.run.failed`, свежесть лога). Запускать после обновлений ZCode и при подозрении; кандидат для `zcode-doctor`.
8. **Исходники** живут в репозитории hub: `it/zcode/hooks/guard/` (под git); установка копированием через `install_guard.py` (dry-run, бэкап, слияние). `~/.zcode/cli/config.json` не создаётся вручную.
9. **Приватность.** Команды не покидают машину; логи локальные, права 600, секреты подменяются best-effort, у разрешённых вызовов Bash пишутся только имена программ. Внешние сервисы (в т.ч. Jev) не используются.
10. **Политика `yolo` из §6 не меняется.** Hooks делают `yolo` безопаснее, но (см. ограничения) не заменяют запрет `yolo` для проектов с ценными данными.

## Ограничения (известные и принятые)

Это **страховка от ошибок модели, а не граница безопасности**. Hook не видит: содержимое скриптов (`python -c`, `bash script.sh`), команды, собранные через переменные (`g=git; $g push` — только пометка `NOTE-dynamic-command` в логе), обход через кодирование вне известных шаблонов, `git pull` на main (неявный merge), `git config --global`. Определение путей в Bash эвристическое; для `Write`/`Edit`/`Read` путь приходит готовым и проверка надёжна. Разбор строк ловит намерение, а не гарантирует исполнение. Невидимы для hook и действия вне ZCode (ваш терминал).

## Последствия

- (+) `git push`, `rm -rf`, запись вне workspace и в эталонные данные, `git add .env` получают формальную преграду во всех режимах, включая `yolo`.
- (+) Shadow-журнал даёт данные для настройки правил до того, как они начнут мешать.
- (−) Появляется ещё один компонент Level 0 со своей поддержкой; ложные срабатывания будут раздражать, пока правила не отстроены (поэтому shadow).
- (−) При обновлении ZCode формат hooks может измениться: проверять `--doctor`.

## Альтернативы

- **Только правила в `AGENTS.md`**: текущее состояние, не защищает в `yolo`.
- **Запретить `yolo` целиком**: не решает ошибок в `build`, ограничивает эксперименты.
- **ML-классификатор (Jev) в hook**: отклонено на этом этапе (данные уходят наружу, ранний доступ, внешняя зависимость в критичном месте); можно вернуться, если в журнале накопятся пропуски, которые правила не ловят.
- **Блокировка только по `mode`**: поле ненадёжно (факт 4).

## Открытые вопросы

1. Работает ли `ask` (тест C) и как выглядит запрос в UI.
2. Видимость вызовов субагентов workflow подтверждена (проба 09.10, см. «Контекст»); остаются: блокировка субагентов в `enforce`, субагенты инструмента `Agent` (вне workflow), `deny` в `build`/`edit`.
3. Нужен ли `PostToolUse` для аудита результатов.
4. Вынести `protected_data_names` и разрешённые корни в `.zcode/project.yaml` каждого проекта (нужна схема).
5. Поправка Level 0 (по вашему подтверждению) — добавить в раздел «Безопасность»:
   > Hub-guard активен. При отказе hook не обходи запрет другим способом: сообщи причину пользователю и жди явного разрешения.
